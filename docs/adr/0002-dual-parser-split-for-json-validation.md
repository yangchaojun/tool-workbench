# JSON 校验采用双解析器分工：引擎造值，自写解析器找错

校验定位需要跨浏览器一致的精确 行:列 与可读错误原因，而引擎 `JSON.parse` 的报错格式不保证可解析。我们决定：值一律由 `JSON.parse` 产生（Unicode 转义、数字精度等语义零风险）；自写的容错解析器**只在** `JSON.parse` 抛错时启动，专职定位错误，不产出数据。树形视图与压缩/格式化输出也吃 `JSON.parse` 的结果，因此树、报错、输出三者不存在解析分歧。

一个未来读者会问 “为什么树和报错不用同一个解析器”——因为单解析器必须逐项复刻 JSON 语义（数字精度、转义、重复键），测试面大一个数量级，而收益仅是架构上的整齐。误报风险以兜底规则消除：自写解析器找不到错时，降级显示引擎原始报错。

## Consequences

- 自写解析器只需实现 “错误检测 + 位置计算”，代码量约为单解析器方案的十分之一。
- 若未来出现需要 AST 而非值的消费者（如 JSONPath 查询），再评估提升为完整解析器，届时应重新审视本决策。

## Revision 2026-09-05（工具升级为 JSON 编辑器时）

Consequences 中预言的「AST 消费者」场景到来（查询、对比、树形编辑落地），但评估结论是本决策**维持不变**：查询引擎（JSONPath/JMESPath）、对比与树形编辑都直接消费 `JSON.parse` 的值，无一处需要 AST。自写解析器的职责从「错误定位」扩展为「错误定位 + 修复候选」——它在定位骨架上产出候选修正文本，但候选结果仍必须送 `JSON.parse` 验证后才允许呈现给用户，依旧不产出正式数据。
